1. 我看到你简历上写你在这家公司负责 AI Chat 的回复编排、SSE 流式、长期记忆这些。先用两三分钟介绍一下这个产品是做什么的，以及你具体负责的部分？

   - 这是一款ai情感陪伴应用，用户可以和一个ai角色建立长期的记忆关系，他有长期记忆，记得聊过的内容，有rag知识库，还有关系评测，关系天气这类玩法，用户可以在多端体验，web端，telegram，whatsapp，wechat等都可以直接接入，商业化走积分制和vip订阅

   - 技术栈是sringboot3+java17，存储是redis，postgresql，milvus，minio

   - 这期间我主要负责四块工作，按工作量来排的话

   - 最大的一块是实时语音通话的链路，用户在浏览器跟ai打电话，整条链路是，websocket收到浏览器pcm音频，发送给火山引擎进行流式STT转写，转写成文字后复用文本回复编排拿llm流式输出，流式输出到一个分句器切成短句，逐句发送给火山TTS合成，最后音频块边合成边回推给浏览器，同时发字幕事件保证音画同步。（这里面我处理了几个比较有意思的问题：比如用户随时可能打断 AI说话，需要一套中断机制保证正在跑的 LLM 和 TTS 能被及时取消；比如回合切换时 STT 残留音频频、TTS尾巴音频这些竞态；还有分句策略要在延迟和听感之间做权衡）

   - 第二块是多平台接入的统一编排，三个平台的消息格式、鉴权方式完全不一样，Telegram 是 webhook，微信是轮询，WhatsApp 是带签名校验和防重放的 webhook，我做的核心是把入站收敛成一个平台无关的统一事件模型，所有平台走同一个处理器入口，出站通过一个回复端点接口反转回各平台，另外还做了一层协调器处理去抖和同一会话的串行化

   - 第三块是 MinIO 对象存储管附件和媒体文件那套存储体系

   - 第四块是 Prompt 的统一管理，把 prompt模板从代码里抽到数据库，做了版本化、发布状态和热加载

   - 除了这四块业务开发，我还独立负责整个产品的部署和云上运维


2. 你说独立负责整个产品的部署和云上运维，具体做了什么？
   - 产品是 snowie-ai.com，海外业务，跑在 AWS 上，从域名到服务器整条链路都是我搭的：
   - 域名在 GoDaddy 买的，但 DNS 解析权交给 AWS Route 53（NS 指向 Route 53）
   - 主站流量走 CloudFront 做 CDN 和 HTTPS 入口，证书在 ACM（us-east-1，自动续期），前面还挂了一层 WAF（速率限制 + AWS 托管规则集），CloudFront 按路径分流：/api/* 和 /ws/* 不缓存直接回源，静态资源和图片走缓存
   - 源站是 EC2（ARM64 Graviton，Ubuntu），nginx 做反向代理，后面是 docker-compose 起的一整套服务：Next.js 前端、Spring Boot 后端、admin 前端、PostgreSQL、Redis、MinIO、etcd、Milvus
   - 源站不用 IP 直接写进 CloudFront，而是用 origin 子域名，以后换服务器只改一条 DNS 记录就行

- 更有代表性的是一次**跨 AWS 账号的全量生产迁移**，旧账号要关闭，所有资源迁到新账号。我的做法是新旧并行，最后短维护窗口切流：
  - 先做资源盘点：把旧账号的 EC2、Route 53 全部记录、CloudFront 配置、WAF 规则、ACM、S3、安全组全部导出成清单
  - 新账号逐项重建：ACM 证书不可导出，只能在新账号重新申请 + DNS 验证（在旧托管区加验证 CNAME）；WAF 按原规则原顺序重建，保持 Count 模式不阻断；CloudFront 重新创建指向新 origin
  - 顺手做了安全加固：旧安全组 SSH 对 0.0.0.0/0 开放，新安全组改成只允许管理员固定 IP；旧服务器上 PostgreSQL、Redis、MinIO 这些数据库端口都暴露在公网，新环境只开 80/443/SSH，内部服务全部收进内网
  - 代码用 rsync 增量同步（不能直接 git pull，因为旧机有未提交的配置修改和版本分叉），最后维护窗口：停掉旧端写入，同步 PostgreSQL、MinIO、Milvus/etcd 的数据增量到新机，验证通过后改 Route 53 切流
  - 迁移已完成，业务无感切换
