## 主线四道

1. 存储这块整体怎么设计的？（开场全貌题，目标 90 秒）

   - 先定位：全站唯一的对象存储底座，管三类东西——聊天附件（Web 上传 + TG/WA 入站图片）、PUA/雷点告警卡片渲染图；另外 Milvus 向量库的对象存储也复用同一个 MinIO 实例，一套基础设施两个消费者
   - 设计上做了两层抽象：第一层是一个极小的接口，upload/delete/generateDownloadUrl/download 四个方法，底下是唯一的 MinIO 实现——接口小是为了换 S3/OSS 时只加实现类，而且 MinIO 本身 S3 兼容，迁移成本极低
   - 第二层是**条件装配整体可关**：`@ConditionalOnProperty` 加 ObjectProvider，配置开关默认关——本地开发不依赖 MinIO 也能把应用跑起来，告警卡自动降级成前端静态图。这个"存储是可降级的能力而非硬依赖"的姿态和多平台、RAG 的设计是一脉相承的
   - key 是单 bucket 多前缀：附件是 `chat/用户/会话/消息/年月/uuid-净化文件名`，告警卡是 `pua-alerts/`、`redflag-alerts/` 前缀。路径即索引——按用户/会话批量清理（合规删除）可以前缀列举直接删；年月做时间分片；uuid 随机后缀防同名冲突也防枚举
   - 为什么单桶不分桶：MinIO 的 bucket 更像权限和生命周期策略的边界，当前所有对象同一套私有读写策略，分桶只增加管理成本；实体里保留了 bucket 字段，为多桶迁移留了 schema 余地
   - 一致性是两阶段写：先传对象再落库，落库失败同步补偿删对象防孤儿——单对象单记录的场景补偿路径简单可靠，上 saga/outbox 这种重机制不值
   - 技巧：先报"Milvus 也复用"（基础设施视角）；"可降级的能力而非硬依赖"是全项目一致的设计姿态，说出来就是架构观；两阶段写配一句"为什么不用重机制" preempt 掉追问

2. 文件的访问控制怎么做的？直接给 MinIO 预签名 URL 不行吗？（本模块最值得讲的设计）

   - 不行，我们三种消费场景用了**三种 URL 策略**，因为消费方不同、信任模型不同
   - **聊天附件：HMAC 自签 URL + 后端代理流**。序列化消息时现算 `?exp=1小时&sig=HMAC(附件id+过期时间)`，请求打回后端，校验过期→签名常量时间比较→查库状态→从 MinIO 取字节代理下发。为什么不用预签名：一是**可撤销可审计**——校验要查 DB，删记录改状态立即生效，而 MinIO 预签名签出去就收不回；二是配置零依赖——预签名 URL 绑死 MinIO endpoint，外部配置不全时签出来指内网根本不可用，代理只需要后端自己可达；三是不暴露 bucket 命名和存储 endpoint
   - **告警卡片：MinIO 预签名 24 小时**。消费方是 Telegram/WhatsApp 的**服务器**（sendPhoto 按 URL 抓图），让平台直接抓 MinIO，后端不经手流量；卡片是一次性推送，24 小时过期即失效。这里有个真踩过的部署坑：SDK 签出来的 URL 指向 Docker 内网地址，外部平台抓不到——解法是把 URL 的 **origin 替换成公网地址但保留签名 query、不重新签名**，前提是反向代理把同路径透传到 MinIO
   - **AI 视觉输入：后端下载 + base64 data URL**。多模态 LLM API 只收公网 URL 或 base64，MinIO 在内网服务商抓不到，只能 base64 内嵌进请求
   - 一句话收束：**访问策略跟着消费方走**——浏览器走可撤销的代理，平台服务器走预签名省流量，LLM 走 base64——对象存储本身只有一套，策略差异全部在 URL 层
   - 技巧：先反问式破题（"直接预签名行吗？不行，因为……"）；origin 替换不重签名这个坑是"真踩过"的铁证；收束句展示这是按信任模型设计而非随手写

3. 用户上传文件，安全上做了什么？（上传链路防御纵深）

   - 大小双保险：Spring multipart 层 10MB 单文件/25MB 单请求——超限连 Controller 都进不去；业务层再查一遍 10MB。两层是因为配置层和代码层会各自漂移，关键限制代码里要有自己的底线
   - 类型校验三段式：IMAGE 走 MIME 白名单（jpeg/png/webp/gif）**加文件头魔数校验**——contentType 来自请求头可以任意伪造，把可执行文件改名 x.png 就能混进来，魔数是文件内容自证；ARCHIVE 走 zip 白名单加**结构防护**——最多 256 个 entry、单文件 12MB，读的时候 readNBytes 超限即拒，防 zip 炸弹；其他类型直接拒
   - 文件名五步净化：Unicode 归一化防变体绕过 → 斜杠替换成横线**杜绝 `../` 遍历和跨目录写** → 空白折叠 → 删非法字符 → 合并截断。防遍历的纵深上有个诚实点：存储层的 key 校验只查非空，安全性完全依赖上游净化——如果未来新调用方忘了 sanitize 就是路径注入，改进是存储层统一拒绝 `..` 和前导斜杠
   - 元数据溯源：每个对象带 messageId/sessionId/userId 三元组——**库里查不到时仍能从 MinIO 侧反查归属**；文件大小取 MinIO statObject 的返回值而不是请求值——以存储侧事实为准
   - 上传本身是流式的：拿 InputStream 直接进 SDK 分片上传，不在 JVM 里拼完整字节
   - 技巧：魔数和 zip 炸弹各自带一句 WHY（可伪造/自证、entry 上限）——安全题答"防什么"比答"用了什么"值钱；主动交代纵深弱的那个点是自信信号

4. MinIO 晚高峰宕机 30 分钟，系统会怎样？（故障推演题，串联全部链路）

   - 分五条链路推演，严重度从低到高：
   - **PUA 告警卡**：渲染上传失败 → Optional.empty → 分发器降级成前端静态图——**有降级**，用户几乎无感
   - **查看历史附件**：代理下载 catch 住 → 404——**可恢复**，MinIO 回来即好，数据无损
   - **语音消息**：完全不碰 MinIO——语音是转写即弃的设计，下载字节→火山转写→只留文本。**不受影响**，这题顺便把"语音为什么不存"答了：价值在文本，音频留存还是隐私和成本负担——按"下游还需不需要原始媒体"决定存不存
   - **Web 附件上传**：事务回滚，消息和附件记录都不落，用户收 500 自己重试——**无半途数据**
   - **Telegram 图片消息**：最严重。入站事件已先落库（RECEIVED），存储抛异常冒到 webhook 返回 500 → Telegram 超时重试 → **重试被 eventId 幂等挡掉** → 消息永不处理，事件行永久滞留 RECEIVED——**半途状态且不自愈**
   - 结论定性：告警卡和查看有降级/可恢复，是因为它们把 MinIO 当旁路；TG 图片链路出问题，根子不在存储而在**入站幂等只防重复、不补失败**——出站有重试 worker、入站没有任何 RECEIVED/FAILED 的补偿扫描，这和我在多平台模块复盘过的是同一个根因，存储宕机只是把它放大了
   - 技巧：按严重度排序列链路 = 推演能力的展示；结尾把锅从"存储"抬到"入站补偿缺失"的根因层，并主动关联多平台模块——证明跨模块看到的是同一个系统

## 第二梯队六道

5. 一张 9MB 的 PNG 从浏览器上传到 LLM 收到，字节被搬运了几次？哪次驻留内存？

   - 形态链：浏览器 multipart → Spring 落**磁盘临时文件**（不占堆）→ getInputStream **流式**进 MinIO SDK 分片上传（不驻留）→ AI 分析时从 MinIO download——`readAllBytes`，**第一次完整驻留**：10MB byte[] → base64 编码成 data URL，**第二次驻留且放大 1.33 倍**：13.3MB 字符串 → 塞进 LLM 请求体发出去
   - 代理下载路径同样有 readAllBytes 加 ByteArrayResource 全量返回——两次放大点同源
   - 最值得优化的是 **AI 路径**：同图多轮对话每次都重新下载重新 base64，纯重复搬运——改 LRU 缓存 data URL 或预生成缩略图（vision 模型根本不需要原图分辨率）；代理路径改 InputStreamResource 流式透传
   - 技巧：能数出"两次驻留、一次放大 1.33 倍"这种精确数字，就是真跟过字节流的证明；优化排序讲理由（AI 路径重复发生 vs 代理路径每次一图）

6. 同一张图从 Web 上传和从 Telegram 发进来，校验一样吗？

   - **不一样，这是个真实的不对称**。两条路从 `storeMessageAttachment` 汇合成一份逻辑，但校验在这之前：Web 路径过 10MB 上限 + MIME 白名单 + 魔数；入站路径只查非空——**无大小上限、无魔数**
   - 可被利用的攻击面：恶意用户通过 TG 发超大图——字节经平台下载进内存（MemoryFile 适配器是 byte[]），无上限即打爆堆内存；伪造 contentType 同理绕过类型意图
   - 为什么会这样：Web 是不可信边界全套防御，入站当时认为"字节来自 Telegram 服务器转发"偏可信——但**消息内容本质是用户可控的**，信任边界划错了
   - 修法：入站下载时限 contentLength、storeMessageAttachment 入口统一走 validateAttachmentUpload——把校验推到汇合点而不是各自的入口，正好和"逻辑收敛"的设计初衷对齐
   - 技巧：这题答好的标志是**自己指出攻击面**而不是等面试官问"有什么问题"——自己模块的不对称自己招

7. 存储这块的安全债务有哪些？（弱点自省题，主动认）

   - 凭证治理：默认凭证 minioadmin/minioadmin 写在配置默认值和 docker-compose 里——和项目里 API key 未加密是同类问题，改进是启动时检测到默认凭证直接拒绝启动、生产强制环境变量注入
   - 密钥复用：附件签名的 HMAC 密钥复用了 auth 的 code-signing-secret——登录码签名和附件授权是两个安全域，轮换互相影响，应独立配置
   - 签名即授权：公开下载只查 status 不查请求者——任何拿到 id+sig 的人 1 小时内可下载，也无法主动吊销（除非改 status）；改进是缩短 TTL 到分钟级按需换取
   - 缓存自相矛盾：响应头说 max-age 10 分钟可缓存，但签名 URL 每次响应现算、exp 一直变——缓存键永远不同，CDN/浏览器缓存实际永不命中；改进是签名按时间桶取整（整点对齐）
   - 技巧：四条按"凭证→密钥→授权→缓存"排，每条带改进——自省题的答法是"我知道债在哪、优先级怎么排"

8. 入站媒体怎么做到多平台统一的？（与多平台模块的交叉点，存储视角讲）

   - 三个构件：策略 SPI（InboundMediaDownloader，supports+download，TG 是 getFile 两步、WA 是直接 GET webhook 给的 URL）+ **MemoryFile 适配器**（把平台下载的 byte[] 包成 Spring MultipartFile）+ 复用同一个 storeMessageAttachment
   - 效果：Web 表单上传和外部渠道图片从 storeMessageAttachment 这一行开始**完全汇合**——key 生成、MinIO 上传、元数据落库、补偿删除只写一份，platform 字段记录来源
   - 语音转写也复用同一个下载 SPI——下载字节喂火山，只是结果不落桶
   - 技巧：这题多平台那边也会被问，两边讲法错开——那边讲 SPI 的设计模式价值，这边讲"汇合后存储逻辑只写一份"的收益

9. 换成 AWS S3 或阿里 OSS 要改多少？

   - 理论上只加一个实现类：接口就四个方法；MinIO 是 S3 兼容协议，MinioClient 直连 AWS S3 endpoint 基本可用——endpoint/凭证/bucket 配置换掉即可
   - 真实的迁移点其实不在代码在**周边**：三种 URL 策略里，预签名要 S3 侧重新对齐（origin 替换 + 反代路径那段部署逻辑）；告警卡的 ExternalPhotoUrlPolicy 私网段拦截逻辑沿用；Milvus 复用同一个 MinIO 这层要在迁移时一起搬——我做 AWS 跨账号全量迁移时，MinIO 数据就是和数据一起 rsync 过去的
   - 技巧：最后一句勾 AWS 迁移故事——存储题自然过渡到运维差异化故事，主动权在自己

10. 附件和告警卡的 key 为什么这么设计？

    - 附件多级前缀的三个用意：路径即归属索引（合规删除按 user/session 前缀列举直接删）、年月时间分片（容量均匀、便于按时间做过期）、uuid32 随机后缀（同名重传不冲突 + key 不可枚举猜测）
    - DB 兜底：(bucket, object_key) 唯一索引——应用层 upsert 判断失效时数据库兜底
    - 告警卡反而简单（`pua-alerts/{uuid}.png`）：一次性推送、无归属清理诉求（虽然这是弱点——卡片图现在也无人清理）、uuid 防碰撞就够了——**key 复杂度跟着生命周期管理诉求走**，不是越花哨越好
    - 技巧：对比附件和卡片的繁简差异并给出理由——证明 key 设计是按需求推的不是模板抄的

## 快问快答

| 问题 | 口径要点 |
|---|---|
| 接口为什么只四个方法？ | 极小接口换实现最便宜；MinIO S3 兼容，S3/OSS 迁移≈换配置 |
| enabled 默认值？ | false——本地开发不依赖 MinIO，应用照常起；告警卡自动降级静态图 |
| 附件 URL 的 TTL？ | 1 小时（HMAC 自签）；告警卡预签名 24 小时；响应缓存头 10 分钟 |
| 签名怎么算的？ | HmacSHA256(attachmentId + ":" + expiresAt)，Base64url 无 padding，校验常量时间比较（MessageDigest.isEqual） |
| 上传上限？ | Spring 层 10MB 单文件/25MB 请求 + 业务层再查 10MB；zip 限 256 entry/单文件 12MB |
| 魔数校验防什么？ | contentType 可伪造——改名 x.png 的可执行文件；魔数是文件内容自证（FFD8FF/89504E47/GIF/RIFF…WEBP） |
| fileSize 记谁的？ | MinIO statObject 返回值，不记请求值——以存储侧事实为准 |
| 落库失败怎么办？ | deleteQuietly 补偿删对象再抛原异常——防孤儿；删除失败只吞（不掩盖原始异常） |
| 启动时 MinIO 挂了？ | ensureBucketExists 抛异常 bean 创建失败——fail-fast 起不来；enabled=false 时 bean 不装配照常起 |
| 语音为什么不存？ | 价值在文本；音频留存是隐私+成本负担；失败兜底 IGNORED+提示发文字 |
| putObject 之后为什么还 statObject？ | 回读存储侧事实（etag/size/contentType）——已知多余：putObject 返回值本身就带 etag，可直接用（改进项） |
| MemoryFile 是什么？ | byte[]→MultipartFile 适配器——平台下载的字节伪装成 Spring 文件接口，才能复用 Web 上传那套 storeMessageAttachment |

## 已知弱点弹药（追问"有什么问题"时用，按被问概率排序）

1. **入站媒体无大小上限无魔数**（Web/入站校验不对称，可被超大图打爆内存）→ 校验推到汇合点统一做
2. **下载全量进内存 ×2 放大**（readAllBytes + base64 1.33 倍；AI 路径每轮重复搬运无缓存）→ InputStreamResource 流式 + data URL 缓存/缩略图
3. **孤儿对象无回收**（删会话只级联删 DB 行，对象永久残留；卡片图同样不清理）→ lifecycle 过期 + 对账 job 或前缀批删
4. **默认凭证提交仓库**（minioadmin/minioadmin）→ 启动拒绝默认值 + docker secrets
5. **附件签名密钥复用 auth secret**（两安全域互相影响轮换）→ 独立 signing-secret
6. **签名即授权不可吊销**（只查 status 不查请求者）→ 短 TTL 按需换取
7. **Cache-Control 与 URL 设计矛盾**（exp/sig 每次现算 → 缓存键永远变，缓存永不命中）→ 时间桶取整
8. **防遍历只在最上层**（存储层 key 校验只查非空，全靠上游 sanitize）→ 存储层统一拒 `..`/前导斜杠
9. **AI 视觉无缓存**（同图多轮重复下载+base64）
10. **zip 解析在事务内**（12MB/256-entry 占 DB 连接）→ 挪事务外
11. **putObject 返回值弃用 + 多余 statObject**（多一次网络往返）
12. **ObjectProvider 每次方法调用 getIfAvailable**（语义上没必要，微小开销）
