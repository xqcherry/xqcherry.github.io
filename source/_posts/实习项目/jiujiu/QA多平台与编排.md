## 主线四道

1. 把多平台接入这条链路从头到尾讲一遍（目标 2 分钟，超 3 分钟就是失败）

   - 好的，先交代一个背景约束：我们产品主体是 Web 端 AI 聊天，业务上要求同时覆盖 Telegram、WhatsApp、微信三个 IM 平台，而且三个平台的用户和 Web 用户必须是**同一个账号、同一套记忆、同一套计费**。所以这条链路的核心命题是：**业务逻辑写一份，平台差异全部压到适配器边界**——模板收敛加平台适配
   - 以 Telegram 文本消息为例。第一步是接入层：webhook 进来先过 secret 校验，用常量时间比较防时间侧信道；解析器把平台原始报文转成一个统一的中立事件 `InboundChannelEvent`——12 个字段，平台专有的交互（比如 TG 按钮点击）被"信封化"塞进文本字段，核心链路永远只看到文本和媒体列表
   - 第二步是平台服务，三个平台是同构的六步骨架：eventId 幂等检查（防平台重推）→ 事件落库 → 查身份绑定 → 未绑定发绑定引导 → 已绑定做平台特殊分流（语音先转写、测评关键词、按钮拆信封）→ 最后全部汇入 ChatHandler 这个单入口
   - ChatHandler 做平台无关的事：解析平台会话到站内会话的映射（会话按关系档案隔离，不按平台账号）、用户消息先落库、图片经策略 SPI 下载后落对象存储
   - 然后提交给协调器 ExternalChatReplyCoordinator——这是我做的最核心的一块：**latest-wins 去抖 + 按路由键串行 + 防重入**，保证同一聊天窗口内回复有序、用户连发消息只回最新，这块您可以细问
   - 协调器内部复用 Web 端同一个 ChatReplyOrchestrator 做多 Agent 编排——记忆注入、意图识别、PUA 和雷点检测、积分扣费，三端一份代码自动继承，只是输出换成了 Noop 适配器，结果由协调器拿 outcome 二次投递
   - 最后回发：出站反转适配器 ReplyPort 把回复发回原平台，底下走统一投递服务，幂等键加落库加重试队列。这条链路全程跑在 webhook 容器线程上，一条消息占用 10 到 30 秒——这是已知要优化的点
   - 技巧：背景约束（同账号同记忆同计费）先立住，"写一份业务逻辑"是题眼；协调器处放慢给钩子；结尾主动认线程弱点展示知道边界

2. 用户在 Telegram 上连发 3 条消息（间隔 2 秒，LLM 生成要 8 秒），最终会收到几条回复？怎么保证不乱序、不轰炸？（简历"统一会话编排"的拷打位）

   - 答案：收到 1 条回复，针对第 3 条消息，但上下文包含全部三条（用户消息在协调器之前就已落库，主模型拉的是会话全量）
   - 机制是一个 ConcurrentHashMap 加每路由一个小状态对象，**没有队列、没有线程池**。每条消息进来提交到协调器：要么成为 runner 在当前线程同步跑回复，要么只更新"最新请求"槽位立刻返回
   - 时序走一遍：第 1 条消息成为 runner 开始生成；第 2、3 条到达时 runner 在跑，它们只做一件事——**无条件覆盖 latest 槽位**，这就是去抖，注意它是语义去抖"只回最新"，不是时间窗去抖，没有 timer
   - 第 8 秒第 1 条生成完，落库前有个 staleGuard 检查：latest 的消息 ID 已经不是自己 → 抛 Superseded 异常——所以这条的 token 已经花了（LLM 跑完了），但**不落助手消息、不扣积分、不回发平台**，事件标成 SUPERSEDED。runner 回到循环头取最新，对第 3 条跑完整流程后投递。数据库里第 1 条是 PROCESSED 加 SUPERSEDED errorCode，第 3 条 PROCESSED，第 2 条停在 RECEIVED——它从没被编排器处理过
   - 串行性靠 RouteKey 四元组：平台、平台用户、外部会话 ID、线程 ID。同一聊天窗口串行，不同用户、不同群、不同话题天然并行。防重入靠 running 标志加细粒度锁，submit 要么当 runner 要么搭便车
   - 三个机制各防什么：去抖防"5 个 LLM 回复轰炸用户"，串行防"回复 2 先于回复 1 到达"，防重入防"同会话两个线程并发跑 reply"
   - 技巧：先报答案（1 条）再讲机制，直接展示推演过；"语义去抖不是 timer"是区分度最高的一句；最后主动点破"被顶替的 token 白烧了"——这是 L3 追问点，先认比被问出来强

3. 你说多 Agent 协同，具体怎么编的？为什么有的串行有的并行？（bullet 2 直接拷打位）

   - 整体是**串行主干 + 并行旁路**：意图识别串行，PUA/雷点两个检测和主生成并行，最后还有标题生成、测评 CTA 这些收尾动作
   - 意图必须串行，因为它的结果决定"要不要走主回复"——命中测评意图直接短路去发测评卡片，根本不跑主生成。但串行代价压到了三层兜底：显式关键词规则快速通道不调 AI；AI 调用带 2500ms 硬超时；异常兜底转成"走主流程"。所以它快、且永远不会把主链路卡死
   - 检测和主生成并发，因为检测是**旁路咨询**——PUA 命中只是在主回复后追加告警，不拦截不改写，它没资格挡在主路前面。前置串行的代价是每次回复先付一次检测 LLM 往返，用户首字延迟翻倍；后置则告警要多等一整个检测时延。并发让检测时延（1-3 秒）被主生成时延（5-30 秒）掩盖，主流程走到等待点时 future 大概率已经完成——经典的把旁路延迟藏在关键路径后面
   - 稳定性的核心契约是**检测链永不失败**：配置关了返回不匹配；当天已告警过去重直接跳过；模型超时、HTTP 失败、JSON 坏、DB 错——全部在 exceptionally 里折叠成一个"信息不足"决策，等价于不告警。异常永不出检测域，绝不打断主聊天
   - 每日去重也有讲究：按**用户时区**算自然日，且锚点用触发消息的 createdAt 而不是 now——不然消息实际发生在昨天，跨时区查重会算错天。并发兜底靠数据库唯一索引，撞 23505 按"今天已告警"处理而不是报错
   - 技巧："串行主干 + 并行旁路"六个字先定性；每个 WHY 都落在"延迟"和"稳定性"两个产品约束上；结尾"检测链永不失败"是契约级表述，比"做了异常处理"高一档

4. 积分扣费怎么做的？用户余额不够怎么办？

   - 顺序是：**生成前预检，生成后按真实用量扣费，扣费失败物理删除消息**。为什么不是先扣费——因为成本只有生成完才知道，usage 是 token 级的，生成前只能做预估预授权，要一整套预留、对账、多退少补机制，复杂度不值；预检先把余额为 0 的用户拦掉，避免白跑主生成
   - 扣费本身是分层的：先花今天会过期的免费日额度，再花手动赠额，最后花 VIP 额度；余额不够覆盖的部分直接 waive——比如余额 3 成本 5，扣 3 免 2，记成 CAP_TO_ZERO。产品上的权衡：不把用户卡在"差一点钱"的半路，最后一次使用免费，余额压到 0 而不是负数
   - 这里有个面试官爱追的细节：预检过了、扣费还是可能失败——预检和扣费之间有窗口，并发的其他消息或检测任务把余额扣到 0。兜底就是 catch 到余额不足后**物理删除**刚落库的助手消息再抛——没有付费的内容不能留在历史里，否则用户刷新拉历史就白看了。删除是物理删除不是状态标记，"生成物"没付费就不该存在
   - 事务边界要讲清楚：reply 整个方法没有事务，落库、扣费、删除补偿是**三个独立事务**——所以这个回滚是 Saga 式补偿，不是同一个事务的 rollback。风险窗口是落库成功、扣费失败、删除前崩溃，会留一条"已落库未计费"的脏消息——改进方向是消息加"待计费"状态加定时对账。顺序上也有讲究：先扣费再生成标题和告警，计费失败时回滚面最小
   - 追问"改成先扣费再落库怎么设计"→ 预授权额度按历史 P95 token 用量估，生成后按真实 usage 对账多退少补，超时未落库由对账任务释放预留。两个方案的失败窗口对比：先落库方案的窗口是"落库到删除之间"；先扣费方案的窗口是"扣费到落库之间"——本质都是用补偿换一致性，差别在脏东西是消息还是钱
   - 技巧：先把顺序报出来再讲 WHY；"生成物没付费就不该存在"是金句；事务三段论必须主动讲——这是区分"读过代码"和"理解设计"的点

## 第二梯队八道

5. 为什么搞统一事件 + 单入口，每个平台各写一套 service 不是更简单吗？

   - 算账：幂等、绑定检查、会话映射、媒体落库、计费、去抖——这些是**平台无关的业务不变量**。三平台各写一套是 12 处漂移点，写一份语义天然一致，比如去抖对所有平台同时生效
   - AI 编排完全复用：三个平台最终都调同一个编排器，Web 端改了记忆注入，三端自动继承
   - 收敛的手段是两个反转：出站用 ReplyPort 接口（核心层定义、平台层实现、方法参数注入），入站媒体用策略 SPI。新平台接入约等于 5 个新文件：解析器、平台服务、ReplyPort、媒体下载器、配置
   - 诚实点（面试官必追开闭原则）：有两处必须改老代码——出站底层投递的 platform 分支和附件平台枚举不是 SPI，这是设计不对称的残留，改进方向是抽 OutboundSender 策略接口
   - 替代方案想过：Spring Integration、Camel 这类 EIP 框架能做但太重，三个平台的规模不值得；事件总线异步化会丢掉"同步控制流 + 路由内串行"的确定性，而这个确定性正是协调器要自己实现的核心
   - 技巧：这题是架构判断力题，"12 处漂移点"的算术最直观；主动交代两处 switch 是自信不是示弱

6. PUA 检测在 8 秒超时了，这条链路上会发生什么？检测结果到底丢没丢？

   - 表面上：编排层等 future 最多 9 秒拿到降级值"信息不足"，不告警，主回复照常——**用户视角什么都没发生**，这就是"检测链永不失败"契约的兑现
   - 但底下没停：orTimeout 只是把 future 标记为异常完成，**不会中断底层线程**——检测任务还在 commonPool 上继续跑，因为它内部那个 AI 调用的 block 没带超时参数（对比意图识别是带 2500ms 的）。它照常跑完三件事：AI 调用完成、检测费照扣——**钱扣了，结果没人消费**；如果命中了 PUA，告警还照常落库——**当天去重额度被消耗**，后续消息查重返回"今天已告警过"，这条告警用户永远看不到；commonPool 线程被一个注定丢弃的任务继续占着
   - 所以答案精确说是：**决策丢了，副作用没丢**——钱、去重额度、线程，三个副作用都留下来了
   - 改进方向：给检测 client 的 block 加超时对齐意图识别；或超时后主动 cancel；或改成"先落库、超时后前端下次拉取补看"
   - 顺带把双超时讲了：future 自身 orTimeout(8s) + 编排层 get(9s)，加 1 秒缓冲是刻意的——保证 exceptionally 先触发、get 拿到的是友好降级值而不是裸 TimeoutException
   - 技巧："决策丢了，副作用没丢"是这题的金句，一句话证明真读懂了 orTimeout 语义

7. SSE 的 chunk 为什么要包 JSON？气泡分隔符从模型吐出到前端渲染成 4 个气泡，中间经过什么？

   - chunk 包 JSON 是被 SSE 规范坑出来的：`data:` 冒号后第一个空格会被浏览器剥掉——delta 以空格开头时（英文缩进、Markdown）**首空格静默丢失**；裸文本里的换行还会拆成多个 data 行。包成 `{"chunk":"..."}`，空格换行都在 JSON 字符串里被转义，前端 parse 还原，parse 失败还留了裸文本回退兼容旧后端
   - 气泡链路有两层缓冲，各防一件事：
   - 第一层在流适配器：永远扣住最后 64 个字符不发，流结束后拿数据库的最终文本和已流式文本求公共前缀，把没发过的部分一次性补发——**终态对账**，即使 provider 流式丢 delta，前端最终也对齐 DB
   - 第二层在分段转发器：每次发完扣住"可能是 `<<<BUBBLE>>>` 前缀"的尾部，防止分隔符被一个 delta 从中间劈开后前半截被当正文发出去；看到完整分隔符才通知前端开新气泡；到第 4 段后停止接收——模型违规输出 5 段以上时防御性截断
   - 落库用同一个分隔符重新切分，每段一条消息，所以 done 事件里的消息列表就是数据库事实
   - 技巧：两个具体损坏场景（行首空格、换行拆行）必须能说实例；"两层缓冲各防什么"用一句话对仗收尾

8. 三个平台的 webhook 安全分别怎么做的？

   - Telegram：header 里带 secret，比较用 MessageDigest.isEqual **常量时间**——String.equals 遇到第一个不同字节就返回，攻击者可以通过响应时间逐字节猜 secret（timing attack）；isEqual 全长度比较，耗时与差异位置无关。配置层 WEBHOOK 模式加空 secret 启动直接 fail-fast
   - WhatsApp 是最完整的一套，Stripe 同款方案：签名是 HMAC-SHA256(secret, **timestamp + "." + body**)——把时间戳绑进签名，意味着截获请求的人既不能改 body 也不能改时间戳，动一个签名就失效；再配 ±300 秒时间窗防重放，取绝对值——**未来的时间戳也算过期**，防攻击者把时间写未来绕过"只挡旧消息"的实现漏洞；比较同样走常量时间
   - WeChat 没有公网回调入口：入站靠带 bot_token 的服务端长轮询拉取，信任边界变成"谁能拿到 bot_token"，而 token 只在扫码确认后由微信下发存服务端——没有可伪造的入站面
   - 追问"TG 为什么不用时间戳防重放"→ 防重放的目的是不重复处理，TG 靠 eventId 幂等兜住：重推的旧请求即使验签通过，eventId 查重直接短路，不会产生重复回复——**安全目标不同层次达成**
   - 技巧：三平台三种模型（对称 secret / HMAC+时间窗 / 无入站面），展示"安全是按信任边界设计的"而不是背方案

9. WhatsApp 把同一条消息的 webhook 重推了 3 次，第一次处理到一半进程崩了——用户最终能收到回复吗？

   - 答案：**收不到**。第一次：事件已落库（RECEIVED）、AI 没跑完、进程崩了。后两次重推：existsByEventId 命中——幂等检查直接静默吞掉，连日志都不带重试。事件永远停在 RECEIVED，这条消息没有回复
   - 换成"进程不崩、但 AI 编排抛了非业务异常"也一样：事件标 FAILED、异常上抛，平台超时重推——还是被幂等吞掉。结论一致：**用户永远收不到回复，且系统层面没有任何补救**
   - 这暴露的是幂等设计的不对称：**出站有完整的重试体系**——投递任务落库、线性退避重试 5 次、15 秒定时扫到期任务、5 次失败进死信；**入站只有一个 check-then-act 的查重，没有任何 RECEIVED/FAILED 状态的补偿扫描**。幂等防了"重复回复"，但把"该回复而没回复"也一起挡掉了
   - 改进方向：给入站事件加对账——定时扫超时未 PROCESSED 的事件重新入队；或者幂等命中时检查旧事件状态，FAILED 的允许重处理
   - 技巧：这题答好的标志是先给结论再给"不对称"的定性——出站 at-least-once、入站是"至多一次"，这是消息系统的经典权衡，能点出来就是 L3

10. 协调器收尾时的 remove 有什么讲究？听说这里有竞态？

    - 先讲带值 remove：`routes.remove(key, state)` 只删"自己放进去的那个值"——普通 remove(key) 在并发下可能删掉别的线程刚新建的 state，把人家的路由状态偷走
    - 竞态本身：收尾线程在锁内置 running=false 并 remove；此时另一个线程已经拿到旧 state 对象但还没进锁；它进锁后置 latest、看到 running=false、成为 runner——用的是**已经出队的 state**；再来第三个线程 submit 会新建 state2 也成为 runner——同一个路由两个线程并发跑 reply，可能双回复
    - 窗口极窄（锁释放到 computeIfAbsent 之间），但存在。修法三选一：不 remove，改用带 TTL 的后台清理——顺便把竞态修掉，但 state 对象按路由数常驻内存；用 routes.compute 原子复核；或者每路由固定一个单线程 executor，彻底消灭"谁来当 runner"这个问题
    - 为什么当时这么写：单机单实例、路由数有限，ConcurrentHashMap 加细粒度锁是最小实现；真要上多实例，这套内存态协调本身就要换成分布式方案（Redis 锁或消息队列按路由分区），remove 竞态只是小问题
    - 技巧：先讲带值 remove 的正确性（多数人答不出），再讲竞态——层层递进；结尾把话题抬到"多实例怎么办"的高度，主动引向架构演进

11. 这条链路的线程模型？200 个用户同时发消息会发生什么？

    - 先报账：Web 端整条 reply 主干跑在 ForkJoinPool.commonPool（runAsync 没指定 executor），两个检测任务也在 commonPool——**每条 Web 消息占 3 个 commonPool 线程**，全是秒级到分钟级的阻塞任务；外部渠道走 webhook 容器线程或轮询线程；语音有自己的 cachedThreadPool
    - commonPool 并行度约等于 CPU 核数减一。200 并发消息：前几个占满池子，后面全部排队——**所有用户的回复和检测一起停摆**，而且 parallelStream 这些隐式使用者也被拖死，是系统级故障；更糟的是 orTimeout 超时不释放线程，饱和会自我加速
    - 改造：主干和检测各配**专用有界线程池**，supplyAsync 显式传 executor，池间隔离——检测再慢也拖不死主回复；有界队列满时快速失败比无限排队好
    - 虚拟线程在这**是好选择**：这些任务全是阻塞 IO 模型（等 LLM、等 DB），不占 CPU，虚拟线程天然为"海量阻塞任务"设计，一行改动换掉 commonPool；要注意的是它救不了"下游 LLM 被打挂"的场景——背压和限流是另一层问题
    - 还有个部署相关的雷：TG 轮询模式跑在 Spring 默认大小为 1 的调度线程池上，AI 回复同步跑在里面会把**所有 @Scheduled 任务一起拖死**，包括出站重试——修法是轮询只管拉取、处理丢业务线程池
    - 技巧：先报"每条消息占 3 个"这个数——数字是推演过的标志；虚拟线程题不要只喊好，主动说出它救不了什么

12. 现在要接第四个平台 Discord，怎么做？

    - 纯新增五个文件：平台枚举加值；webhook Controller 加 UpdateParser（产出统一事件，语音消息包成 InboundMedia）；DiscordChannelService 照六步骨架抄（幂等→落库→查绑定→引导→分流→ChatHandler）；DiscordReplyPort；语音下载器实现 InboundMediaDownloader SPI——Web 端和三平台已有链路零改动
    - 语音在哪层转写：平台服务的分流层，照 Telegram 的做法——先经下载器 SPI 拿音频字节、走火山一次性转写、把事件改造成文本事件再进 ChatHandler。放这层是因为转写依赖平台专属的文件下载方式（Discord 要先拿 attachment URL），而下载已经被 SPI 隔离好了
    - RouteKey 映射是关键决策：externalChatId 映射频道 ID（私聊是用户 ID、服务器是频道 ID），externalThreadId 映射 Discord 的 thread ID——这样"同一频道串行、不同频道并行"，与 TG 群话题的处理一致
    - 必须改老代码的两处要主动说：出站投递服务的 platform 分支要加 Discord 路由；附件平台枚举要加值。改完顺手动把出站也 SPI 化，把这次接入变成偿还设计债的机会
    - 技巧：这题是 L4 设计题，答的核心不是清单而是**分层意识**——什么该新增、什么必须动、RouteKey 映射决定并发语义，最后一句"借机把出站 SPI 化"是加分项

## 快问快答

| 问题 | 口径要点 |
|---|---|
| RouteKey 是什么？ | (platform, platformUserId, externalChatId, threadId) 四元组；TG 话题级粒度，WA/微信退化为账号级 |
| 去抖是时间窗吗？ | 不是——latest 槽位无条件覆盖 + run-to-completion 只消费最新，语义去抖"只回最新"，没有 timer；消息持续到达时每轮仍会回一条，不饿死 |
| 被顶替的消息，token 花了吗？ | 花了——staleGuard 在 AI 生成完之后、落库扣费之前才检查；改进是把检查下沉到每个 chunk 回调 |
| 幂等键怎么设计？ | 入站 event_id 唯一索引（防重推重复回复）；出站幂等键 = eventId + ":reply:" + 段序号（防重复发送） |
| 意图识别为什么能串行不拖慢？ | 规则快速通道不调 AI + 2500ms 硬超时 + 异常转走主流程，三层兜底 |
| 每日告警去重怎么算"一天"？ | 按用户时区解析 localDate，锚点用消息 createdAt 不是 now；并发兜底靠唯一索引撞 23505 |
| CAP_TO_ZERO 是什么？ | 余额不够覆盖就 waive 差额、压到 0 不欠款——体验优先，量级极小 |
| NoopChatReplyOutput 是什么？ | 外部渠道不需要流式推送，输出全丢弃，结果由协调器拿 ChatReplyOutcome 二次投递——端口适配器思想的实例 |
| WeChat 为什么没 webhook？ | 协议不支持，扫码登录后每账号一个长轮询线程；绑定在扫码时就双向完成，不存在未绑定消息 |
| bind token 怎么防一个平台账号绑两个用户？ | 消费走存在性检查 + `(platform, platform_user_id) WHERE status='ACTIVE'` 部分唯一索引兜底，第二个 insert 必撞 |
| 出站图片为什么要做 URL 可达性检查？ | TG/WA 服务端自己抓图，内网 URL 抓不到；拦 localhost/私网 IP；微信是后端先下载再传所以放行 |
| 简历写的"参考 OpenClaw"是什么？ | ⚠️ 需要准备：能一句话讲清 OpenClaw 的适配思路和我们的差异——见待填窟窿 3 |

## 已知弱点弹药（追问"有什么问题"时用，按被问概率排序）

1. commonPool 承载全部异步（每条 Web 消息 3 线程、orTimeout 不释放、无命名）→ 专用有界池 / 虚拟线程
2. TG 轮询模式单调度线程跑 AI → 拖死所有 @Scheduled → 拉取与处理分离
3. webhook 同步占容器线程 10-30s → 立即 202 落库 + 异步消费（协调器就是现成骨架）
4. supersede 白烧 token → staleGuard 下沉到 chunk 回调（语音链路有现成范式）
5. orTimeout 不取消底层检测 → 钱扣了结果没人消费、去重额度被消耗 → client 加 block 超时
6. 回滚非原子（三个独立事务 Saga）→ save 与 delete 之间崩溃留脏消息 → PENDING_BILLED + 定时对账
7. 入站幂等无补偿（出站有重试、入站没有）→ FAILED/RECEIVED 事件永远没人管 → 定时对账重入队
8. 协调器 remove 竞态可能双 runner → 不 remove + TTL 清理 / 每路由单线程 executor
9. 检测 future 在积分预检之前启动 → 欠费用户白烧两个检测调用 → 预检前置
10. 出站投递 at-least-once + 多实例无锁 → 可能重复发消息 → ON CONFLICT 抢占式入队
11. 出站路由和附件平台是 switch 不是 SPI → 与入站侧设计不对称 → 抽 OutboundSender
12. bind token 为复用加了明文列 → DB 泄露时未消费 token 直接可用 → 重签发替代存明文

## 拷问走势图

```
介绍完项目（自我介绍/简历 bullet 1、2）
  ├─ A: "展开讲讲多平台怎么接的" → 主线1 链路走读 → 钩子指向协调器
  │      → "用户连发消息怎么办" → 主线2 三件套 → supersede → 白烧 token（弱点4）
  │      → "为什么不用消息队列做串行" → 内存态设计的边界 + 多实例演进
  ├─ B: "多 Agent 怎么协同" → 主线3 串行/并行 → "检测超时呢" → 第二梯队6 → commonPool（弱点1）
  ├─ C: "计费怎么保证不出错" → 主线4 → "预检过了还失败？" → 窗口 + Saga → 事务三段论
  ├─ D: "安全怎么做的" → 第二梯队8 三平台安全 → "重推呢" → 第二梯队9 幂等不对称
  └─ E: "再接一个平台要多久" → 第二梯队12 Discord → 开闭原则诚实点（弱点11）
```

核心结论：**三件套（去抖/串行/防重入）+ supersede 时序 + 事务三段论**必须练到脱口而出——A/C 两条最高频路径最终都汇到这三处；所有线程类追问最终汇到 commonPool 一题。
