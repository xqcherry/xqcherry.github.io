# 语音通话链路 — 面试 Q&A

> 链路详解见 code-walk/jiujiu-web-语音通话链路-详解.md，产品开场见 QA.md 第 1 题。
> 主线四道脱稿讲，第二梯队按点背，快问快答一句话过。

## 主线四道

1. 你刚才讲得比较快，能把这条语音链路从头到尾再讲一遍吗？（目标 2 分钟，超 3 分钟就是失败）

   - 好的，我按一个回合的数据流来讲，讲之前先交代两个背景约束
   - 第一是压首音频延迟——用户说完话到听到 AI 开口，这个等待直接决定这个产品能不能用
   - 第二是用户随时会打断——AI 说到一半用户开口，必须立刻停下来进入收音状态
   - 一个是快，一个是停得干脆，整条链路的取舍都在这两点上
   - 链路本身：连接是两步的，浏览器先走 HTTP 建一个通话会话，拿一张一次性票据，再用 WebSocket 带票握手——因为浏览器原生 WS 没法带自定义 header，这是 WS 鉴权的标准做法。连上之后二进制帧就是音频，PCM、16k、单声道，直接喂给火山引擎的流式 STT，转写的 partial 结果实时推给前端做字幕
   - "用户说完了"的判定是三路的：客户端主动 commit；服务器这边起了一个 200ms 周期的调度任务，检测到 700ms 没有新音频就判定说完，做兜底；另外 STT 自己也会给 final。三路谁先到都行，入口用一个 CAS 保证只有一个能真正提交回合
   - 提交之后不走单独的语音逻辑，而是复用我们文本聊天的回复编排器——这样长期记忆、RAG、计费这些能力语音和文字就是同一套，语音侧只是换了一个输出适配器：文本那边是 SSE 推流，这边是字幕加 TTS 管线。我觉得这是这块设计里最值钱的一个决定
   - 然后是延迟优化的核心：LLM 的流式输出不攒，过一个分句器切成短句，第一句切出来立刻送 TTS，开始合成、开始播放，后面一边生成一边继续切、继续合成——它是一条流水线。首音频延迟就约等于 LLM 首 token 加一句短句的合成，而不是等整段生成完。音频块边合成边回推浏览器，同时按段号发字幕事件，音画是对齐的
   - 麻烦的地方在并发：打断要同时停掉 LLM 侧和 TTS 侧的线程和外部会话，还有回合切换时 STT 的残留回调、TTS 的尾巴音频这些竞态。我们为此做了一套"线程取消加回调点检查"的双保险机制，这块您可以细问
   - 技巧：先讲约束再讲数据流=拉开差距；"复用编排器"处放慢给亮点；结尾钩子指向打断（准备最深的地方）

2. 技术难度最大的是哪块？（挑什么=判断力考点）

   - 难度最大的是打断和它引发的一串并发问题，其他环节——接 STT、接 TTS、分句——本质是集成和调优，难的是有一套正确性要自己保证的并发模型
   - 具体说：用户打断的时候，系统里同时有一个 turn 线程正阻塞在 LLM 的流式读取上、一个 TTS 消费线程在等队列或者等火山返回音频、两个外部服务会话（火山的 STT 和 TTS 各一条 WebSocket），还有一个 endpointing 的定时任务，打断要把这六样东西按顺序全部停下来，任何一样漏了都会出体验问题——比如 TTS 没停干净，AI 会"打断之后还在自顾自说话"
   - 第一层是线程取消：future.cancel(true)、关火山会话、cancel 定时任务。但 cancel(true) 只是"尽力打断"——线程可能正卡在不可中断的阻塞里，比如网络 IO
   - 所以有第二层，回调点主动检查：LLM 每个 chunk 到达的回调开头都查一次"当前回合还有效吗"，不有效就抛中断异常——这是最频繁的检查点，保证最多多吐一个 chunk 就停；TTS 的音频回调同样检查，过期音频直接静默丢弃。两层缺一不可：cancel 负责叫醒，检查负责确认死透
   - 再往深一层是竞态：三路 endpointing 并发到达，靠入口 CAS 防重复提交；打断瞬间旧回合的 LLM 回调还在路上，靠回合号隔离——回调带着旧 seq 来，比对当前活跃回合号不符就丢
   - 还有一个比较隐蔽的：STT 的回调不属于任何回合，打断后重启收音是"新一代" STT，所以给每次收音加了一个自增的代际号，迟到的旧回调靠它识别，防打断后旧 STT 把残留文本写进新回合
   - 技巧：开头先亮判断力；金句"cancel 负责叫醒，检查负责确认死透"；三件套讲到代际号最深的点就收，留一层给追问证明有余量

3. 用户说完到听到 AI 回复，延迟多少？瓶颈在哪？（有埋点=王牌）

   - 我们对这条链路做了全链路分段埋点：从用户停止说话开始，STT 出 final、LLM 出首个 delta、TTS 出首段音频，四个时间点分别打点，日志直接输出每段的耗时——瓶颈落在哪一段一目了然，不靠猜
   - 打点看下来，大头是 LLM 的首 token，通常一到两秒；STT 判定说完到 final 几百毫秒；短句 TTS 合成首包也是几百毫秒量级
   - 优化全部围绕"别等"来做，三个动作：
   - 一，流水线化——原来等 LLM 整段生成完再送 TTS，改造后第一句切出来就开始合成播放，把"整段生成时间"从首音频延迟里整个拿掉了
   - 二，首段分句激进切短——分句器给第一段单独设了更激进的阈值，12-18 个字就强切，专门抢首包；后续段落放宽到至少 24 字才切，因为段太碎 TTS 韵律差、每段合成任务开销大——首延迟和听感是一对矛盾，用不同阈值分别照顾
   - 三，TTS 消费端先启动——回合开始就先把队列消费者拉起来等着，第一段一到零延迟开跑
   - 优化后首音频延迟约等于 LLM 首 token 加一句短句合成，体感"跟真人对话差不太多"。再往下压就要动 LLM 首 token 本身了（模型选型、预测式合成），那是另一个量级的工程
   - 技巧：第一句抛"分段埋点"，从背数字变成展示工程方法；"不靠猜"是题眼；主动收尾展示知道边界

4. 为什么不直接用 OpenAI Realtime API？（选型题）

   - 当时评估过，没选托管方案，三个原因：
   - 第一是成本。Realtime 按音频 token 计费，比 STT+LLM+TTS 三段自组贵不少。我们商业化是积分制，语音又是消耗积分最重的场景，成本直接进毛利，放大到通话时长上是很大的数
   - 第二是控制权。我们要的几个东西托管方案给不了或给得很别扭：分句粒度要自己控，它是首延迟和韵律之间的权衡旋钮；字幕要跟音频段严格对齐；打断后要立刻恢复收音；还有跟现有体系整合——语音每句回复要走同一套记忆注入、RAG、计费的编排器。自研链路每一环都能改，托管只能接受它的口径
   - 第三是供应商解耦。STT、LLM、TTS 三段分开，每段都能单独换供应商，事实上我们 LLM 侧本来就是多模型的。托管等于三段绑死一家
   - 当然自研不是免费的——代价是并发正确性全要自己兜，比如打断和竞态那套机制，用托管就不用自己写了。但我们的判断是：成本和控制权的收益长期大于这部分维护成本
   - 技巧：三个理由落到产品具体处境（积分制、通话时长、多模型），泛泛说"更灵活"减分；最后主动承认代价=算过账的高光时刻
   - 追问"以后 Realtime 成熟了呢"→ 如果它计费降下来、开放更多控制点，这个架构切过去也不难，因为我们三段本来就是解耦的——把问题弹回架构优势

## 第二梯队六道

5. 通话中途网络断了，怎么办？

   - WS 断开：afterConnectionClosed 做完整清理——endpointing 定时任务、STT 流、turn 线程、TTS 会话全部 cancel，会话关闭。当前实现没有断线续传：通话中断就是回合终止，前端重新走 HTTP 建通话、拿新票据、重连。会话不"丢"——每条消息实时落库，重连回来上下文还在，只是当前回合 AI 说了一半的话没了
   - 网络抖动但没断：WS 走 TCP，抖动表现为延迟而非丢帧，STT 流式本来就是为这种容忍设计的。真正要防的是抖动期间的迟到回调：旧 STT 的转写在打断后才回来，靠代际号识别成过期直接丢，不污染新回合
   - 要做断线续传的话：给通话会话加短 TTL 恢复窗口，重连带旧会话 ID 恢复状态——但当时判断性价比不高：情感陪伴场景重连成本可接受，先把回合内正确性做扎实
   - ⚠️ 危险在于编"有重连机制"——追问票据一次性就穿帮。诚实承认+为什么不做+怎么做能做=反而加分

6. 打断是谁判定的？服务器怎么知道用户在 AI 说话时开口了？

   - 打断的触发在客户端：前端用本地 VAD（音量/语音活动检测）判定用户开口，发一个 interrupt 控制消息过来。服务端不自己判定——因为 AI 的声音正从同一个浏览器扬声器放出来，服务端收到的音频流混着 AI 自己的回声，靠服务端判定要先做回声消除，不如浏览器自带的 getUserMedia echoCancellation 可靠
   - 服务端收到 interrupt 后做的是执行：按序 cancel 六样东西——endpointing 定时任务、STT 流、回合状态（回合号清零+收音代际自增）、turn 线程、TTS 线程、火山 TTS 会话——然后立刻重启收音，用户打断完马上能说
   - 隐含的分工：判定在端上（离信号源近、有回声消除），执行和正确性在服务端。误触发也安全：interrupt 处理是幂等的——没有活跃回合时就是清理一遍状态，没有副作用
   - 亮点表述："判定在端、执行在服务端"——证明对端到端链路有完整认知

7. 聊天用 SSE、通话用 WS，为什么传输层不统一？

   - 按需选的。文字聊天是单向的——请求走普通 HTTP，回复是服务端往客户端推流，SSE 完全够用且更简单：跑在普通 HTTP 基础设施上，浏览器原生自动重连，nginx/CDN 支持都是现成的
   - 语音必须 WebSocket，两个硬需求：双向（上行音频+下行音频和控制消息同时跑）、二进制帧（PCM 音频，SSE 是纯文本通道，base64 编码音频既浪费带宽又丑）
   - 两个场景在服务端是同一个编排器、两个输出适配器——SSE 的 emitter 和 WS 的字幕加 TTS 管线。传输层差异被适配器吸收，业务逻辑不感知
   - 技巧：最后一段主动引回王牌（复用编排器）——表面考传输协议，实际送分题

8. 多个线程要往同一个浏览器连接发消息，怎么处理的？

   - 往同一个 WS session 写数据的不止一个线程：Tomcat 容器线程收消息、STT 回调线程推字幕、TTS 音频回传线程推二进制帧。WebSocket session 不是线程安全的，并发写会帧交错，文本帧和二进制帧混在一起协议就坏了
   - 做法：所有发送统一收敛到带 synchronized(session) 的两个方法——发事件、发音频——单连接内串行化。粒度是 per-connection 的，不同通话之间不互相影响
   - 代价心里有数：客户端收得慢时 sendMessage 阻塞在锁里，会拖住同一条通话里其他写者的线程。改进方向是异步发送+每连接一个发送队列，写者只入队不等待。当时没做是因为单通话内并发写者就两三个，没成为瓶颈——但高并发下这会是问题之一
   - 技巧：弱点主动认+讲清楚为什么当时不做（不是没想到，是没到瓶颈）=知道边界的表达方式

9. THINKING/SPEAKING 期间用户还在说话，音频被丢了？

   - 对，二进制帧只在 LISTENING 状态接收，其他状态直接丢弃——这是设计不是缺陷，原因两层：
   - 一，其他状态下 STT 流根本不存在——回合提交时旧 STT 已 cancel，音频收下来也没有去处；二，SPEAKING 期间浏览器扬声器在放 AI 的声音，收音混着回声，本来就不能要
   - AI 说话时用户开口怎么办？走打断那条路：前端 VAD 判定+interrupt 消息，打断把状态打回 INTERRUPTED，服务端立刻重启 STT 进 LISTENING——"丢音频"的窗口只有打断传递的一两百毫秒，用户体感是"我一开口它就停了"
   - 状态机：CREATED → LISTENING → THINKING → SPEAKING → INTERRUPTED → 回到 LISTENING 循环。所有状态迁移点都有原子检查，比如回合提交入口是 CAS，防三路 endpointing 并发提交两次
   - 技巧：这题听着像缺陷（"丢了？"），要立刻扭话头——"是设计，原因两层"。被动挨问和主动定性，印象完全不同

10. 这条链路怎么测试的？

    - 分三层
    - 纯逻辑层单测：分句器是纯函数式的——append delta、吐切好的段——四级边界、最小长度、残余 flush 都有确定输入输出，最好测，比如"首段 12 字无标点应切在 18 字"、"60 字无边界强制切"。竞态防护关键方法（CAS 提交、代际判定）也是纯逻辑，直接测
    - 集成层靠埋点日志联调：四段延迟打点就是干这个的——一条日志看全链路。打断的时序问题肉眼看不出来，但埋点能把"打断发生在第几段音频之后"拍得很清楚
    - 端到端真机测：真实浏览器+真实麦克风，重点测打断——AI 说到一半开口、连续快速打断、打断瞬间 STT 残留。语音的东西 mock 不出回声、抖动这些真实条件，最终一定要真机
    - 最难测的是竞态本身——时序依赖，单测难复现。我们的策略是把竞态正确性做成结构上可推理的：CAS、代际号每个机制都单独简单到可以证明，组合起来靠代码评审兜底，而不是靠测试撞运气
    - ⚠️ 第一层和第三层要按真实做过的事填细节（真实写过的用例、真机踩过的坑）——见文末待填窟窿

## 快问快答

| 问题 | 口径要点 |
|---|---|
| 为什么选火山？ | 国内可用、流式 STT/TTS 协议成熟、按量计费适合初期；且三段解耦设计本来就是为了随时能换 |
| 语音通话怎么计费？ | 走同一套编排器的计费逻辑（积分制），语音跟文本消息同构——⚠️ 具体口径需确认当时按什么计的，别现编 |
| awaitDone 30s 超时是干嘛的？ | 防 TTS 卡死拖住回合线程；弱点是超时只抛异常不主动 cancel TTS，极端时线程滞留——已知改进点 |
| ticket 被截获怎么办？ | 一次性+短时效，握手拦截器验票同时校验会话归属（requireOwnedActive），拿别人的票也连不上 |
| 重新设计你会改什么？ | 固定线程池或虚拟线程替代 cachedThreadPool、有界队列加背压、异步发送队列、同用户通话抢占——按"量级上来了先坏哪个"排序讲 |
| 团队多大，这块谁写的？ | 语音链路是我独立负责的（call/speech/tts 三个包）——语气要稳，不要谦虚 |

## 已知弱点弹药（追问"有什么问题"时用）

1. 无背压：TTS 队列是无界 LinkedBlockingQueue，LLM 快于 TTS 时段落堆积 → 有界队列+阻塞入队，背压自然传导回 LLM
2. cachedThreadPool 无上限：每通话至少 2 常驻线程 → 固定大小或虚拟线程（Java 21）
3. 同步 WS 写：慢客户端拖住其他写者 → 异步发送+每连接发送队列
4. 打断无全局锁，靠原子标志+CAS+generation 协同，正确性靠兜底而非证明
5. awaitDone 30s 超时只抛异常不 cancel TTS
6. 同用户多通话无限制（registry 按 callSessionId，无 per-user 抢占）
7. STT 持续有声时无强制提交上限（700ms 静音兜底失效场景）
8. 分句按字符集切，英文缩写 Mr.、小数点 3.14 会误切 → 承认+改进方向是 LLM 分句或规则+词典
