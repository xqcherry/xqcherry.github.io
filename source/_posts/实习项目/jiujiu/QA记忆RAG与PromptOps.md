## 主线四道

1. Prompt 管理这块怎么做的？（亲手做的模块，开场主场题，目标 2 分钟）

   - 背景先立住：prompt 是这个产品迭代最频繁的"策略资产"——主 persona 已经改到第 9 版，历史上 14 个 Flyway 迁移全是改 prompt。每次调词都要发版，运营等不起，所以我把 10 个 LLM 提示词从代码抽到了数据库
   - 数据模型是两张表：模板表存"这个 prompt 是什么"，key 是业务身份，带一个 current_version_id 指针指向当前生效版本；版本表存"它说过什么"，append-only——每次修改都是新版本行，历史不可篡改
   - 状态机三个态：草稿、已发布、已归档。发布动作在一个事务里做三件事：把旧的已发布版本全部归档、新版本置为已发布、指针改过去，然后驱逐缓存。回滚是**拷贝式**的——把旧版本复制成新草稿再发布，版本号只增不减，还留了 sourceVersionId 溯源
   - 读取链路三级兜底：TTL 缓存 → DB 当前版本 → 代码默认值。代码默认值和 seed 是同一份数据（PromptDefaults），DB 是热路径、代码是安全网——prompt 库挂了只 log.warn 降级，聊天主链路零感知，降级结果还会负缓存 60 秒防止打爆 DB
   - 热更新两层保障：发布自动 evict（秒级生效）+ TTL 60 秒兜底——即使 evict 有竞态漏掉，最坏一分钟也自愈
   - 配套还做了三件事，证明不是裸 CRUD：管理后台前端页（草稿编辑+版本表+发布回滚按钮）；prod→dev 的快照同步脚本（导出 JSON 入 git，dev 启动自动对齐，解决环境漂移）；persona prompt 的离线 A/B 评测脚本——固定用例集加评分 rubric，judge 模型打分出报告，改词先跑评测再上线
   - 技巧：第 9 版、14 个迁移这些数字是做过事的证明；"DB 是热路径、代码是安全网"是设计感金句；最后配套三件套把题从 CRUD 抬到工程化

2. 长期记忆怎么实现的？（"我记得你上次说过什么"怎么落地）

   - 先讲业务形态：产品是关系教练，记忆的对象不是用户本人，是用户和某个关系对象（男友/前任/婆婆）之间反复出现的**雷点和甜点**两类，所以记忆挂在关系画像维度，不挂用户维度
   - 两条链路，一读一写。**读是同步的**：每次聊天前，拉这个画像下最近更新的雷点和甜点各 Top50，按 30 条、2000 字符双预算截断拼成 system 块注入；预算紧张时雷点优先——风险信号比甜点回忆重要，这是产品决策。整个注入 try-catch 包住，记忆系统挂了绝不阻塞聊天
   - **写是异步定时的**：调度器每 60 秒扫一遍开了记忆的画像，有**静默门控**——最近一条用户消息距今不足 300 秒就跳过。为什么这么设计：用户还在倾诉时抽取，语义是残缺的；静默五分钟约等于这轮说完了，而且批量抽整段对话，模型看得到完整叙事上下文，token 也摊薄。所以静默不是省成本，是**等对话说完再抽**
   - 抽取用独立的便宜模型（gpt-4o-mini 级别，独立配置独立计费渠道），输出结构化 JSON：每个记忆点带标题、详情、发生明细。落库有三层去重：第一层模型自己看全量旧点做**语义合并**（返回 existingPointId 挂旧点，且 ID 必须是 prompt 里给过的，防幻觉）；第二层 contentHash——type+title+detail 规范化后 sha256，可建唯一索引、确定性、零成本；第三层 messageId 幂等，防即时雷点链路和后台抽取对同一消息重复计数
   - 增量靠 createdAt 游标：只抽上次处理点之后的新消息，游标和写库在同一个事务里
   - 追问"为什么 hash 不用语义相似度"→ 语义去重已经交给 LLM 那一层了，hash 只做确定性兜底；embedding 相似度没法建唯一索引、阈值今天判重明天判不重、每次还要推理成本——分层去重里每层只干自己擅长的事
   - 技巧：开头"记忆挂在关系维度不是用户维度"先讲清业务形态，这是别人没有的认知；"等对话说完再抽"是 WHY 金句；三层去重按层报，每层一句话说清挡什么

3. RAG 这块怎么做的？（先亮定位再讲技术）

   - 定位先说：这条链路是团队设计、我完整读过且能讲清取舍，我自己在同文件的上下文构建里改过附件注入部分
   - 一句话：管理端维护全局知识库（恋爱沟通方法论），写入时双向量——Ark 2048 维稠密加本地 512 维稀疏；聊天时拿**最后一条用户消息**做混合检索，Milvus 服务端 0.7/0.3 加权融合取 top3，命中非空才注入知识上下文 system 块
   - 为什么混合检索：两路失败模式互补——稠密管语义召回（"跟男朋友吵架了"能召回英文的 conflict 文档），但对精确词面弱；稀疏管词面精确命中且本地计算零成本。权重 0.7/0.3 是经验默认值，做成了配置项留了调优口子——诚实讲没做过自动调参
   - 稀疏向量的实现有个容易讲错的点：它**不是词典/BM25**，是 hashing trick——token 哈希进 512 个桶累加词频再 L2 归一化，免训练免词典的 bag-of-words。主动纠正这个说法反而证明真读过代码
   - 工程姿态："我把 RAG 当**可降级的旁路增强**而不是主链路强依赖"——整个检索包 try-catch，embedding 挂了、Milvus 挂了都返回空，聊天照常；命中为空也不注入（空块只会教模型硬套知识库）
   - 注入块里带了防幻觉指令：知识库内容和用户自述矛盾时不许编、要追问澄清；score 一起给模型让它自己权衡
   - 技巧：开头定位声明一句就够，不要反复强调不是自己做的（越描越黑）；"可降级的旁路增强"是这题的姿态金句；hashing trick 纠错是亮点

4. 你说个性化回复——用户画像、记忆、知识检索这些上下文最后怎么组装起来的？（三模块的汇合点）

   - 都汇在一个 ChatContextBuilder 里，每次回复按固定顺序拼 system 块：**persona → 语言指令 → 长期记忆 → 关系天气分数 → 附件归档 → RAG 知识块 → 历史消息**，历史只取最近 50 条，四类系统生成消息（测评卡片/告警图等）不进上下文防污染
   - 每一路都有自己的降级和开关，这是设计上的一致性：记忆挂了返回空块；RAG 挂了返回空列表；prompt 取不到回落代码默认值——**没有任何一路增强是聊天的硬依赖**，主链路的最坏情况永远是"没有个性化，但能回复"
   - 有一个我觉得最巧的设计是 `{{MEMORY}}` 条件插槽：注入前先探测线上 persona 模板里有没有这个占位符——有就把记忆**内联渲染**进 persona 正文，没有就作为独立 system 消息追加。含义是**记忆注入的位置由模板作者（运营）决定**，而两种情况都不会丢记忆、不会重复注入
   - 因为语音通话也复用同一个编排器，这套上下文组装对语音同样生效——记忆、RAG、个性化是渠道无关的能力
   - 技巧：这题答好的标志是能报出**顺序**（说明真组装过）+ 每路的降级（说明理解"增强 vs 依赖"的分层）；{{MEMORY}} 插槽是你亲手模块和团队模块的连接点，讲它最自然

## 第二梯队八道

5. 一个全新部署（没人碰过 prompt 后台），用户聊了一个月，记忆表里会有 AI 抽取的数据吗？（我发现的真 bug，可当 STAR 讲）

   - 答案：**没有**。推理链：代码里的默认抽取 prompt 要求模型输出 `{"points":[...]}` 格式；启动时 bootstrap 把它 seed 成已发布 v1；但解析器读的是 `redflags` 和 `sweets` 两个数组——schema 脱节了
   - 后果链：模型按 prompt 返回 points → 解析器两个 path 都是 MissingNode → 判空直接 return → **抽取永远空转，而且游标照推**——这批消息被标记为已处理，永远不会再抽。一个月后表里只有手动创建和即时雷点链路写的数据
   - 为什么会发生：prompt 演进过（redflags/sweets+occurrences 是后来的 schema），代码默认值没跟上——典型的"两处真相漂移"。线上没爆是因为 prod 的这个 prompt 已经被运营改到 v2（快照可见），大概率已经是正确 schema；坑的是全新部署
   - 我是怎么发现和验证的：读抽取链路时对不上 prompt 和解析器的字段——然后推理"全新部署会怎样"得出这个结论；验证方法是测试环境全新起一套，发消息等静默期过，查表和 audit log
   - 修法：默认 prompt 同步成 redflags/sweets schema，或解析器兼容旧 points 格式双读
   - 技巧：这题是最好的"深度阅读证明"——不是背出来的，是推出来的；讲的时候按"现象→推理链→为什么线上没爆→修法"四步走

6. 记忆抽取失败了怎么办？崩溃和失败是一回事吗？

   - 不是一回事，这套设计里两者语义刻意不同：**进程崩溃/事务回滚**——occurrence 没写、游标没推（同事务），下轮**重抽**，at-least-once，靠 messageId 幂等防双计；**逻辑失败**（AI 超时、JSON 解析失败、计费不足）——异常被 catch 吞掉，但 finally 里游标照推——**永久漏抽**，at-most-once
   - 这是刻意选择"失败即放弃"：避免坏消息无限重试阻塞唯一的调度线程，代价是这段对话少学一条记忆——损失可接受。宁漏勿堵
   - 把时间线算一遍：用户 23:59 发完最后一条 → 静默 300 秒 → 00:04 才具备抽取资格 → 调度器 fixedDelay 60 秒，最早 00:04 左右、最晚 00:05 扫到。如果那一刻 AI 超时——catch 吞掉、游标推进，这批消息永久漏抽
   - 漏抽的真实场景还有个刺：计费在写库**之前**，余额不足抛异常 → 同样吞掉推游标——欠费用户的消息被"处理过"了但什么都没学到
   - 改进：区分可重试失败（不推游标+重试上限）和内容性放弃（推游标），加死信审计
   - 技巧：崩溃 vs 逻辑失败的分法 + "宁漏勿堵"四个字是这题的骨架；时间线题（23:59 那道）就在这里顺手答掉

7. 即时雷点（聊天线程）和后台抽取（调度线程）同时写同一个记忆点，计数会出问题吗？

   - 会。计数是 JPA 读-改-写——两边同时读到 count=5，各 +1，先后 save，后写覆盖前写，**丢一次更新**。实体没有乐观锁版本号，明细表也没有 (memo_point_id, message_id) 唯一约束，纯先查后插有竞态窗口
   - 现有防护只有一层：messageId 先查后插的存在性检查，用的是 Postgres jsonb 的 `@>` 包含查询——查"这个点名下任一明细的 messages 数组里有没有这个 messageId"。它**缩小**了窗口但没有消除
   - 两个索引层面的缺失：明细表没有唯一约束兜底并发插入；`@>` 查询没有 GIN 索引支撑，明细多了以后每次幂等检查都是线性扫
   - 改进三件套：计数改原子 SQL 自增（`SET count = count + ?`）；加唯一索引 + 捕获 23505 当"已计过"处理；GIN 索引或干脆把 messageId 拆成独立列
   - 技巧：先答"会"再画两线程时序；"缩小窗口但没消除"这种精确表述比"有竞态"高一档

8. 发布新 prompt 后，有用户还在用旧版本，怎么回事？

   - evict 发生在发布事务**提交之前**——方法内先 evict 缓存再返回、事务才提交。并发请求可能在"evict 之后、commit 之前"重查 DB，拿到的还是**旧内容**并重新入缓存，这份脏缓存再活 60 秒
   - 这是标准的"先更新 DB 再删缓存"时序问题，只是这里顺序反了：变成了"先删缓存后提交 DB"。修法：evict 挪到 `TransactionSynchronization.afterCommit` 里，或延迟双删
   - 为什么线上没出大事：TTL 60 秒兜底，最坏一分钟自愈——所以整体是"秒级生效的目标 + 分钟级的最坏保证"
   - 顺带把版本号竞态也认了：草稿的 max+1 取号无锁，两个管理员同时存草稿会撞唯一索引报 500——兜底在但体验差，改法是 DB 序列或 FOR UPDATE
   - 技巧：能主动讲"这是标准的缓存一致性时序问题、我们顺序反了"——承认已知反模式比辩解值钱十倍

9. prompt 渲染有什么坑？用户能攻击它吗？

   - 渲染是 String.replace 字面量替换 `{{KEY}}`，不是正则——pattern 侧无需转义，这是对的。坑在**逐参数单趟循环**：如果参数 A 的值里含 `{{B}}`，而 B 在 A 之后替换，注入的占位符会被二次替换，且 Map 迭代顺序不定、行为不确定
   - 真实暴露面：标题生成把用户首条消息原文当参数传——用户打一句带 `{{maxChars}}` 的消息就可能被替换掉——**用户内容进了模板参数**，这是注入隐患
   - 另一个静默问题：模板里拼错的 `{{MEMMORY}}` 或调用方没传的参数，占位符**原样进入最终 prompt**，不校验不报错
   - 手写修法：单趟正则 `\{\{\w+\}\}` 扫描 + 按 match 查表替换，值本身永不再扫描；未匹配的占位符记日志；用 `Matcher.quoteReplacement` 防 value 里的 `$` `\` 被解释
   - 技巧：这题答到位 = 证明对"模板引擎为什么都要单趟扫描"有理解，不是背 API

10. 要求 prompt 变更支持 5% 用户灰度、出问题自动回退，你怎么改？

    - 版本表加两个字段：流量百分比 + 一组回退指标（或先人工回退）。发布动作从"归档旧的+指针切换"改成"新旧并存，按比例分流"
    - 路由点在 getPublished：按 userId 哈希取模落在哪个桶就用哪个版本——**哈希必须稳定**（同一用户永远同一版本），这是 A/B 的前提
    - 缓存 key 要变：现在是 PromptKey 一维，灰度后必须变成 (PromptKey, versionId) 二维，否则缓存会把不同用户的版本串掉——这是这题真正的考点
    - 自动回退：埋评测信号（用户中断率、负反馈、对 persona 类 prompt 可上线上 judge 抽检），指标越界自动把流量百分比归零——指针回拨即回退
    - 现成基础：离线评测已经是 baseline vs candidate 的 A/B 形态了，缺的只是线上分流——所以这是增量不是重写
    - 技巧：缓存二维化是这个设计题里区分度最高的一步，先说它

11. 记忆为什么挂在"关系画像"上而不是用户上？

    - 语义正确：用户对 A 男友的雷点（"他总是已读不回"）对 B 朋友完全不适用——记忆内容天然属于"某段关系"
    - 演进证据：最早游标确实挂在 users 表上，后来建 relationship_profiles 整体迁移、删掉旧列——**从用户级改到关系级是一次真实重构**，migration 链条完整（V16→V34→V41）
    - 隔离即安全：记忆表双外键 user_id + profile_id，唯一索引按 profile；归档关系后调度器直接不再扫它；资源访问全走"当前活跃画像"校验，访问非活跃画像的资源直接 403——一个用户同时只有一个 active 画像
    - 计费和审计也按画像归集；时区也从用户链式解析——记忆的 pointDate 用用户本地日历日，跨时区不会把深夜倾诉记成第二天
    - 技巧：V16→V34→V41 是"看过 migration"的硬证据；"用户画像 ≠ 关系画像"的分层顺手讲掉（简历里"用户画像"的措辞落点就在这）

12. 记忆多了以后老记忆会沉底，要做重要性衰减怎么设计？

    - 先认现状：注入排序是 updatedAt 降序——最近动过的优先，没有任何语义相关性和重要性概念；occurrence 每次追加都会刷新 updatedAt，所以它近似"最近活跃度"代理，老记忆确实永远沉底
    - 三个现有字段逐一评估：pointDate（这件事发生在哪天）适合做时间衰减锚点；occurrenceCount 适合做衰减的**减速因子**——发生次数多的记忆衰减更慢，这正是"高频雷点应该更牢固"的直觉；updatedAt **不适合**——它被写入行为污染，"被更新"不等于"重要"
    - 改造点在 MemoryContextService：拉取从 Top50 by updatedAt 改成按 `occurrenceCount^α × exp(-λ·Δdays)` 之类的复合分排序（DB 端算或拉大候选池内存算），pointDate 缺失时回退 createdAt
    - 更激进的方向：复用现成的 rag 向量基建，按**当前消息**做语义检索记忆——把"注入"从"最近改动"变成"和这轮话题相关"，这是从时间维度到语义维度的升级，基建是现成的
    - 技巧：先答"updatedAt 为什么不行"（被污染的特征工程直觉），再给公式和落地方法——这题考的是特征选择不是背方案

## 快问快答

| 问题 | 口径要点 |
|---|---|
| 雷点/甜点是什么？ | 仅两类：REDFLAG（反复冲突模式/情绪触发点/被越界的边界）、SWEET（温暖时刻/积极联结）——AI 抽取时打标，不是算法聚类 |
| 抽取质量怎么兜底？ | Java 正则质量门：title/detail 必须含动作词或事件词，纯抽象描述（"缺乏安全感"）判太泛拒绝——prompt 约束不住的模型偷懒用代码强制 |
| Top50 是什么？ | DB 层候选池保险丝，真正注入受 30 条/2000 字符双预算；排序 by updatedAt（最近活跃），REDFLAG 先拼优先占预算 |
| 静默 300 秒是干嘛的？ | 等这轮倾诉说完再抽——批量抽 token 摊薄+完整叙事上下文，不是省成本 |
| contentHash 公式？ | sha256(规范化(type|title|detail))，normalize 只做 trim/空白折叠/小写——中文基本无归一效果，已知局限 |
| 游标在哪？语义？ | relationship_profiles 表上一列，"已处理过的最后一条 USER 消息 createdAt"，严格大于增量查 |
| 记忆的 AI 是哪个模型？ | 独立 MemoryAiClient，默认 gpt-4o-mini 级便宜模型，独立配置/限流/计费渠道（MEMORY channel），支持 OpenAI 和火山 Ark 双协议 |
| TTL 缓存为什么不用 Caffeine？ | key 只有 10 个枚举、诉求只有 TTL+evict，60 行自实现可读可讲；但知道规模上来后 Caffeine 白得加载锁+命中率统计——"知道什么规模该换"比"永远不用"是好答案 |
| 负缓存是什么？ | DB miss/异常兜底的默认值同样缓存 60s，防止每次请求都打 DB |
| bootstrap 幂等怎么保证？ | "模板存在且指针可解析→直接 return"，只插不改——线上运营改过的词永不被重启覆盖；有开关可关 |
| 死 key 是怎么回事？ | ASSESSMENT_REPORT 定义+seed 了但无调用方——清理项 |
| RAG 的数字卡？ | topK=3 / candidateK=20 / 稠密 2048 维（doubao-embedding-vision）/ 稀疏 512 维 / 权重 0.7:0.3 / COSINE / nprobe=16 / minScore 默认 0 |
| 换 embedding 模型会怎样？ | 集合 dim 建库时定死，dim 校验在 embed 一步 fail-fast 报 expected/actual；本质是"集合重建"问题，校验只是提前拦截 |
| RAG 检索的 query 是什么？ | 最后一条 USER 消息，不是整段对话 |

## 已知弱点弹药（按模块分组，追问"有什么问题"时用）

**PromptOps（自己的模块，弱点要认得最熟）**
1. evict 在事务提交前——脏缓存最坏 60s（标准缓存一致性反模式，有 TTL 兜底）
2. Flyway 迁移原地 UPDATE 版本表，绕过版本机、无审计——和 append-only 设计自相矛盾
3. 渲染顺序注入 + 用户原文进参数（TITLE 的 `{{maxChars}}`）
4. nextVersionNo 并发撞唯一索引报 500
5. 发布即全量无灰度（离线评测是现成的 A/B 形态，缺线上分流）
6. 缓存无命中率观测（key 只有 10 个，量级安全）

**长期记忆（团队设计，讲弱点配"我 review 时发现"）**
7. 默认 prompt 与解析器 schema 不匹配——全新部署抽取永远空转+游标照推（第二梯队 5，最大的一个）
8. 逻辑失败推游标 at-most-once 漏抽（宁漏勿堵的代价）
9. 调度线程池 size=1 被 12 个 @Scheduled 共享，抽取内 .block() 无超时——慢模型拖死全部定时任务
10. @Transactional 包住整个抽取含 AI 调用——长占 DB 连接
11. occurrence 计数读-改-写丢更新 + `@>` 无 GIN 索引
12. 软删复活：用户删掉的记忆 AI 再抽到同内容会复活（hash 命中软删行 setActive(true)），模型不知道用户删过——改 tombstone
13. 注入无相关性排序（弱点 8 第二梯队 12 已展开）
14. 抽取 prompt 塞全量记忆点无截断——点多了 prompt 膨胀、归并质量下降
15. 配置键耦合：记忆调度间隔取自 weather 的配置键——调天气参数连带改记忆行为

**RAG（队友的模块，弱点点到为止不深入）**
16. 无文档切分——整篇一个向量，长文档语义稀释（与工业级 RAG 最大差距）
17. 稀疏路对中文近似失效（按空白分词，中文整句一个 token）——接分词器或升 Milvus 2.5 用内建 BM25
18. 全局知识库无租户/profile 隔离，tags 存而不查
19. requestTimeoutMs 定义了但没用——Milvus 挂起会拖住同步回复线程（catch 接不住 hang）
