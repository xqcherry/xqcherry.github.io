## 什么是agent，如何给agent分模块？



**概括：**agent不仅仅是LLM调用，是一个以大模型为核心的决策引擎，具备自主目标拆解，外部环境感知，工具执行调用的复杂系统 

核心模块：**推理，记忆，工具，感知**

**推理：**这是agent的大脑，利用大模型的能力进行任务拆解，自我反思觉得agent是继续思考还是调用外部工具

**记忆：**这是agent的知识库，记忆可以分为短期记忆和长期记忆，短期记忆可以通过redis或者内存管理上下文窗口，长期记忆可以利用向量数据库进行RAG检索。核心在于记忆管理，比如如何进行高效的记忆压缩，多路召回，防止上下文爆炸，防止上下文丢失

**工具：**这是agent的手脚，模型通过调用工具，后端程序调用外部api实现与软件或程序的交互，例如调用搜索引擎，数据库，或者github的api等

**感知：**这是agent的传感器，负责把非结构化的输入，比如用户输入一段话或者网页api返回的原始json数据，转化为模型可处理的结构化数据，核心在于语义的提炼



### agent和LLM有什么区别?

LLM 本质上是一个复杂的概率预测模型，擅长文本生成和逻辑推理；而 Agent 是一个以 LLM 为核心决策中枢，能够自主拆解目标、感知外部环境、并调用工具执行任务的**复杂系统**



### 追问：agent中是否包含LLM的功能，它们如何协作？

LLM 是 Agent 的核心大脑，Agent 架构中**必然包含** LLM 的功能，通过感知、工具和记忆模块，将 LLM 从一个‘对话框’转变为一个能自主完成任务的‘智能实体’

**如何协作?**

1. 当agent接收到复杂任务，比如（帮我写个爬虫并存入数据库），会利用LLM的能力进行任务拆解，生成规划步骤，同时agent框架会捕获LLM输出中的关键词，挂起推理流，准备调用外部工具
2. LLM阅读工具的api文档，判断当前是否调用工具，生成相应json，agent利用工具模块去执行这个api调用，将返回的原始结果重新翻译成模型可读，LLM拿到反馈判断是‘继续思考’还是‘调用工具’，这个过程形成一个loop，也就是agent的自我思考和过程





## 目前上下文维护的**难点**是什么，解决方案是什么？

1. **Token 成本**：随着对话轮数的增加，上下文窗口的token也逐渐增加，拉高了推理成本，同时回复延迟增大，影响用户体验
2. **注意力涣散：**在长文本下，模型的注意力机制会被大量噪声信息分散，容易忽略中间的关键细节，从而导致逻辑断裂或产生**事实幻觉**

**解决方案：**

- 针对token问题：

  首先，在用户请求到达核心 LLM 之前，我会做一个对话流

  1. **清洗与结构化：** 过滤掉无效的语气词。不再是机械地投喂原始对话流，而是维护一个 **JSON 格式的动态 Profile**（包含用户偏好、当前任务状态、已确认的事实）。这能极大地提高信息密度，减少不必要的 Token 开销。

     **滑动窗口 + 异步摘要：** 内存中只保留最近 $N$ 轮的热数据。对于被‘挤出’窗口的历史，我会调用一个小模型**异步**生成摘要，并更新到全局背景中，确保‘记性’不丢且成本可控。

- 针对注意力与幻觉

  其次，针对长文本带来的注意力涣散问题，我采用 **‘按需唤醒’** 机制

  **混合检索 (Hybrid RAG)：** 全量历史存入向量库。当新问题涉及旧信息时，才通过语义搜索拉取相关片段。

  **双重过滤 (Rerank)：** 检索回来的 Top-K 片段不直接进 Prompt，而是通过一个 **Rerank 模型** 进行精排。只有得分最高、最相关的 Top-3 才会作为上下文喂给大模型。**通过减少不相关的噪声，从根源上降低模型产生幻觉的概率。**

- 最后，在构建最终 Prompt 时，我会利用 **XML 标签** 对‘实时对话’、‘历史摘要’、‘检索片段’和‘结构化 Profile’进行物理隔离。帮助模型更好利用embedding模型识别不同信息的权重





## 如何设计高效的agent上下文维护方案？

我设计的 Agent 方案核心是构建一个**分层的动态记忆架构**，避免 Agent 被冗余信息淹没。

- **短期记忆（滑动窗口 + 结构化 Profile）：** 仅保留最近 5-10 轮原始对话确保语境。同时实时维护一个 **JSON 格式的 Profile**（包含 User_Info 和 Current_Goal），将松散的对话转化为高信息密度的‘事实清单’输入模型。
- **中期记忆（异步增量摘要）：** 当窗口溢出时，触发异步任务。利用小参数模型对历史进行**递归更新**，形成一份不断演进的‘故事梗概’。异步处理确保了主流程零延迟，同时将万级 Token 压缩至百级。
- **长期记忆（混合检索 + Rerank）：** 面对长周期细节，通过向量库进行语义唤醒。关键在于 **Rerank 过滤**，只允许高评分片段进入 Prompt，从根源上杜绝由于 Context 污染产生的幻觉。
- **全局状态（外部 State 维护）：** 依托 **LangGraph** 等框架将任务状态外挂。不完全依赖 Token 记忆，而是通过外部状态机记录 Agent 的进度，确保长链条任务不忘初心





## 目前主流ai模型支持上下文长度是多少？

目前主流模型已进入**百万级（1M+）**时代，主要分为三个梯队：

- **第一梯队（极致长度）：** **Gemini 3 Pro** 和 **Llama 4 Scout** 是领跑者，原生支持 **1M 至 10M** tokens。这为整库代码分析和超长视频理解提供了物理基础。
- **第二梯队（工业标杆）：** **GPT-5**、**Claude 4.6** 以及国内的 **DeepSeek V4**、**Qwen 3.5**。它们的上下文普遍在 **128K 到 512K** 之间。虽然数值不是最高，但其‘大海捞针’的召回精度和推理逻辑稳定性是工业界的首选。
- **技术趋势：** 现在的关注点已从‘单纯堆长度’转向**‘推理成本优化’**，例如 DeepSeek V4 采用的 **MLA (Multi-head Latent Attention)** 架构，极大地降低了长文本下的 KV Cache 显存压力。



### 追问：如果要处理更长的上下文，有什么方案？

当面对超出模型窗口或追求极致性价比的场景时，我会从以下三个维度进行优化：

1. **架构级优化（原生增强）：** 优先启用 **Prompt Caching（提示词缓存）**，针对重复输入的长背景（如 API 文档）降低 80% 的成本和首字延迟；同时利用 **MLA 技术**在显存受限的情况下强行拉长推理窗口。
2. **检索级优化（精细化 RAG）：** 采用**混合检索（Hybrid RAG）**，结合向量搜索的语义能力与关键词匹配的精确度。关键点在于引入 **Rerank（重排序）** 机制，过滤掉 90% 的检索噪声，防止模型被无关片段干扰。
3. **工程级优化（任务分治）：** 借鉴大数据处理思想，采用 **Map-Reduce** 模式先分段总结后汇总，或使用**递归总结**，带着上文摘要滚动处理下文，确保超长任务的逻辑一致性



### 追问：刚刚提到的agent上下文维护跟如何处理长上下文有什么区别？

这两者的本质区别在于：**处理长上下文**是在解决**物理容纳能力**；而 **Agent 上下文维护** 是在解决 **信息信噪比管理**

#### 1. 目标导向不同

- **长上下文处理：** 侧重**“全量召回”**。目标是让模型在 100 万字里精准找到某一个事实，不漏掉细节。
- **Agent 维护：** 侧重**“去粗取精”**。目标是过滤掉执行过程中的冗余日志，防止模型被噪声干扰导致决策幻觉

#### 2. 处理对象不同

- **长上下文处理：** 面对的是**静态存量**（如一份长合同、一整个代码库）优化手段是 RAG、MLA 架构或索引技术。
- **Agent 维护：** 面对的是**动态增量**（如 Agent 边做边思考、调工具产生的中间状态）。优化手段是**主动遗忘**、**分层记忆**和**异步摘要**。

#### 3. 成本与效率逻辑不同

- **长上下文处理：** 是一次性投入。虽然 Token 贵，目的是为了理解全局逻辑（如重构代码）
- **Agent 维护：** 是长跑消耗。如果 Agent 每一步都带着之前的全量日志，Token 会呈指数级增长。因此必须通过**结构化 Profile** 和**状态机（State）**等用极小的 Token 成本维持长效的任务状态
